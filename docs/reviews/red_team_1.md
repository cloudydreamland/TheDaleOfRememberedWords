# 红队评审 #1（2026-09-26 深夜）

> 三个角色对 worddael 的质疑与改进决议。每条质疑必须在后续迭代中被修复、被测试防御、或被明确写入 non-goals。

## 角色一：资深开发者（代码与工程）

**Q1 重叠窗口从句子中间开始。** `overlap_chars=50` 时块首是上一块末尾任意 50 字——RAG 检索命中的块以半句话开头，展示效果差且Embedding 语义被稀释。
→ **决议（R3）**：overlap 起点对齐到句界（找不到句界再退化到逗号界），并纳入"标点卫生"保证。

**Q2 `find_gold_chunk` 只认第一次出现。** gold 子串在文档出现两次且答案在第二处时，评测会把命中记到错误块——评测协议正确性问题。
→ **决议（R3）**：多出现消歧——任一包含该 gold 任一出现的块被检索即算命中。

**Q3 性能从未量化。** 纯 Python 正则递归切分，吞吐多少 MB/s？chonkie 主打"快 2-10x"，我们没有数字就是裸奔。
→ **决议（R5）**：吞吐基准 + perf floor 测试（低于防线即 CI 失败）。诚实结果进 README；不与 chonkie 对比除非同机实测。

**Q4 Markdown 列表/表格未测。** `- item` 行、表格行被行切分切断，表格列错位。
→ **决议（R5 dogfooding 时补测试）**：表格行标记为 atomic 的行内不切（至少不中途断行）。

**Q5 非确定性审查不彻底。** 修了 `hash()`，还有没有同类问题？（结论：`dict` 迭代序 3.7+ 稳定；`set` 仅用于成员判断不保序遍历输出——已排查。）

## 角色二：资深项目经理（产品与采用）

**Q6 采纳摩擦：用户活在 LangChain/LlamaIndex 生态里。** 没人为了切分器换框架；不进生态就是隐形。
→ **决议（R4）**：`worddael.adapters` 提供 LangChain `TextSplitter` 兼容包装（langchain-text-splitters 已在 dev 依赖可真测）；让用户一行代码把 worddael 塞进现有管线。

**Q7 首次成功时间太长。** 装完到"看见价值"要自己找文本写代码。
→ **决议（R4）**：`worddael demo` 一键命令：内置样例 + 偏移量/句尾统计/策略对比一步展示。

**Q8 真实使用证据为零。** 自建语料说服力弱。
→ **决议（R5）**：公版书真实语料 dogfooding（Gutenberg 中文公版，版权安全），产出 docs/dogfood.md：真实文档上的块大小分布、边界质量、异常清单。

**Q9 缺架构文档。** 单贡献者项目，新贡献者读不懂模块关系就等于没有社区。
→ **决议（R6）**：docs/architecture.md。

## 角色三：老板（战略与护城河）

**Q10 chonkie 1.7.0 功能对表（2026-09-26 README 实查）。** 他们有 Sentence/Recursive/Semantic/Late/Neural/Slumber + overlap/embeddings refineries，主打性能，社区大。我们的差异点必须钉死且可验证：

| 差异点 | chonkie | worddael | 状态 |
|---|---|---|---|
| 小-大检索（父子块一等公民） | README 未列 | ✅ chunk_families + 父块级评测 | 已有，继续强化 |
| 可解释切分（每条边界记录成因） | 无 | 计划 R2 | **全网检索无现成工具，旗舰创新** |
| 标点卫生保证（块首尾不断口） | 无 | 计划 R3 | 做 |
| 中文句界深度 + 偏移 fuzz 保证 | 无 | ✅ | 已有 |
| 性能 | 强 | 未量化 | R5 补数字，诚实呈现 |

**Q11 别人做烂的方向不要碰。** Neural/Slumber（模型/LLM 驱动切分）是红海且依赖 GPU/API key——与本项目"零依赖、纯 CPU"的定位冲突。→ **non-goals**，写进 README（R6）。

**Q12 单人维护 + 无用户 = 信任赤字。** 诚实面对：这个项目最大的风险不是技术是信任。缓解：fuzz 测试与基准报告即"可验证的工程承诺"；发布节奏按 launch_checklist 走，不抢跑。
